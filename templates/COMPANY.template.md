# 【テンプレ】会社の仕組み（COMPANY.md）

> 使い方: `<...>` を自分の事業に置き換える。社員（各ルーティン）が毎回最初にこのファイルと絶対ルール、`priorities.md`（今週の優先順位）、自分の役職の手順書を読んでから働く。

<事業の1行説明。例: 「<プラットフォーム>で<商品>を売る個人事業」>。社員はクラウドで動くClaude、社長はあなた。社長はPCを閉じていてよい。

## 組織
| 役職 | 実体 | 頻度 | 仕事 | 手順書 |
|---|---|---|---|---|
| 社長 | あなた | 週1回 | 週次報告を読み、要判断と承認待ちの下書きに答える | — |
| 事業部長 | クラウドのClaude | 週1回（月曜） | 今週の優先順位を `priorities.md` に書く／各部署のレポートをまとめて社長に週次報告を届ける | docs/roles/head.md |
| 開発部長 | クラウドのClaude | 週2回 | 新商品を作り、検収キューに載せる | docs/roles/dev.md |
| 品質管理部長 | クラウドのClaude | 週2回 | 検収と、公開中の商品の定期テスト | docs/roles/qa.md |
| 運用・成長部長 | クラウドのClaude | 週3回 | 監視・不具合修正・公開＋集客の下書き＋お客さん対応の下書き | docs/roles/growth.md |

> 最小なら「事業部長・開発・運用・成長」の3人でもよい。品質管理部長は、商品が増えて「作る人が自分で検収する」危うさが出てきたら足す。
> モデルの目安: 判断が重い役職（事業部長・開発・品質）は上位モデル、定型作業が多い運用・成長は軽いモデルで十分。

商品の流れ: 開発が作る → `review` → 品質が検収 → `pending` → 運用・成長が公開 → `published`。

## 連携表（誰が誰に何を渡すか）
| 渡す側 | 受け取る側 | 何を | どこで |
|---|---|---|---|
| 事業部長 | 全部署 | 今週の優先順位 | priorities.md |
| 開発 | 品質 | 検収してほしい新商品 | work-queue の review |
| 品質 | 開発 | 不合格の理由 | work-queue の blocked |
| 品質 | 運用・成長 | 合格した商品 | work-queue の pending |
| 運用・成長 | 開発 | お客さんの困りごと・改善要望 | requests.md（宛先を明記） |
| 全部署 | 事業部長 | 各レポートと要判断 | reports/*.md |
| 事業部長 | 社長 | 週次報告・要判断・承認待ち | メール or Issue |
| 社長 | 全部署 | 判断と承認 | このファイルと各下書きの status |

## 決裁権限（社員が自分で決めてよいこと／いけないこと）
| 事項 | 社員の権限 |
|---|---|
| 今週の優先順位 | 事業部長が決めてよい（社長の判断の記録に沿う） |
| 公開中のものの不具合修正・追従 | 運用・成長が自分で直して再公開してよい（テスト合格が条件） |
| 公開待ちからの公開 | 運用・成長が1日の上限内で公開してよい（検収合格済みのみ） |
| 検収の合否 | 品質が決めてよい |
| 新商品の開発 | 開発が自分で選び、実装・検収してキューに載せてよい |
| 表示（タイトル・説明・SEO）の改善 | 開発・運用・成長が改善してよい（表示価格と実価格は一致させる） |
| **価格の変更** | 不可。要判断に提案として書く |
| **絶対ルールの変更・例外** | 不可。要判断に書く |
| **規約がグレーな対象** | 不可。作らずに要判断に書く |
| **お金・アカウント・入金先・本人確認** | 不可。触らない |
| 商品の削除・非公開化 | 不可（規約違反状態になった場合のみ一時停止して要判断） |
| 外部への投稿・返信・送信 | 不可。下書き（status: awaiting-approval）を作り、社長の承認を取る |

## 共有ファイル
- `priorities.md` — 今週の優先順位（事業部長が毎週月曜に書く。全員が最初に読む）
- `work-queue.json` — 公開待ちキュー（開発が追加、品質が検収、運用・成長が公開）
- `publish-log.json` — 公開の記録（1日◯本の上限管理）
- `reports/growth-YYYY-MM-DD.md` — 運用・成長のレポート（起動ごと）
- `reports/dev-*.md` / `qa-*.md` — 開発・品質のレポート
- `reports/weekly-YYYY-MM-DD.md` — 事業部長の週次報告（社長向け）
- `requests.md` — 部署間の改善依頼（宛先を明記）
- `decisions.md` — 社長の判断の記録（社員は要判断を書く前に確認し、同じ質問を繰り返さない）
- `drafts/` — 外部向けの下書き（承認待ち）

## 共通の作業ルール
- 作業に入る前に `priorities.md` を読み、そこに書かれた順番で働く（書かれていないことは自分の手順書の優先順に従う）
- 認証情報・トークンは探さない・表示しない（環境側が自動で付ける前提）
- 作業の終わりに必ず記録を残す（レポート更新、必要なら commit/push）
- **迷ったら作らない・公開しない・直さない。理由を書いて要判断に回す**
